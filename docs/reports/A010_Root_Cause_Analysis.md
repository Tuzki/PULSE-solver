# A010 根因调查：输出重复检查、归档重复编码与精度边界

2026-11-02。根据用户要求暂停完整 A010 回放，保留已完成的事件归档，
先调查根因。本报告不宣称 Windows/Linux A010 的 v2 完整回放均通过。

## 已确认的性能根因

### 1. 输出循环反复检查同一完整 Mode

[`stream_emit`](../../src/runtime.cpp#L313) 在每个模拟通道内部调用
`Flow::compatible(*mode)`。同一采样点的 Mode 和 Flow 没有随通道变化，
却重复比较矩阵、约束、残差映射、真实值映射，并构造用于比较的矩阵键。
函数还对每个通道重新查找映射，计算初始 dot 值，随后在兼容情况下又用
`observe` 覆盖这个值。

A010 保存 13 个模拟通道、4 个数字通道；0.5 s / 0.1 us 对应 5,000,001
个采样点。因此兼容性判断的上界为 **65,000,013 次**。空 Flow 的短路分支
会减少一些实际调用，不能把这个上界当成已插桩的精确调用次数。

在一个完整工频周期的 20 ms Linux CPU 采样诊断中：

| 调用路径 | 普通波形输出 | 事件回放 |
|---|---:|---:|
| stream_emit 输出路径 | 66.83% | 71.60% |
| 其中可识别的 Flow::compatible | 26.11% | 30.19% |
| Flow 构造 | 1.99% | 1.31% |

函数百分比为包含子调用的样本占比，彼此重叠，**不能相加**。
输出路径还含必要的信号计算，不能将其中所有时间都叫作可删除的开销。
但高频重复兼容性检查已经有直接证据；Flow 重建不是此诊断中的主要项。
事件回放重用同一个输出函数，因此“改存事件文件”不会自动解决这个问题。

### 2. 最小因果对照证明重复判断确实拖慢运行

在隔离诊断源码中，仅将兼容性判断从通道循环内部提到同一采样点的循环外，
其余源码字节保持不变。所有状态传播、通道计算、有限值/float32 范围检查、
输出上限、事件和时间处理均保留。补丁没有进入正式求解器。

两个诊断版本采用相同 GCC 13.3 Release 编译参数，顺序运行同一原始案例
的 20 ms 窗口、相同 0.1 us 采样与全部通道；此轮未开启 perf 采样。
时间由 `/usr/bin/time` 测量整个原生进程，属于单次诊断，不是正式基准。

| 诊断版本 | 进程墙钟/s | user CPU/s | system CPU/s |
|---|---:|---:|---:|
| 原输出循环 | 27.43 | 27.23 | 0.18 |
| 同一判断每采样点只做一次 | 12.29 | 12.09 | 0.10 |

原循环的 user+system CPU 为 27.41 s，接近 27.43 s 墙钟，说明该诊断主要
消耗在 CPU 工作，不能归因于磁盘写入或 WSL 启动等待。

实测约 **2.23 倍**。全部时间/信号数组逐字节一致，事件日志一致，检查的
事务数、内部/物理状态、软件状态和输出、根查询/失败、模态编译、微步、
回滚及矩阵指数计数字段均无变化。这证明它是可复现的输出层重复工作，
而非只凭采样热点猜测。

[独立诊断补丁](A010_Output_Compatibility_Hoist_Diagnostic.patch) 仅供审计。
不能直接把本次短窗口倍率外推为完整 0.5 s、其他案例或 PLECS 的倍率。

### 3. v2 修复了存储膨胀，但去重仍发生在昂贵编码之后

[`Trajectory::mode`](../../src/trajectory.cpp#L66) 先执行完整 `encode(m)` 和
共享块编码，再检查根 ID 是否已经存在。即使内容早已保存过，仍会重新
构造 Mode 的 JSON 结构并扫描/哈希整个数据树。

20 ms 事件生成采样中，共享块编码约占 **34.26%**，其他模板编码路径约
占 **15.20%**，合计至少 **49.45%** 的样本落在这些编码路径。这里采用互斥
调用路径分类；它不是所有函数包含时间的简单相加。

已完成的 Windows 0.5 s 归档给出了全时长工作量证据：

| 项目 | 数量 |
|---|---:|
| 事务 | 159,037 |
| 初始快照 + 每事务 old/new 快照 | 318,075 |
| 带 Flow 的快照 | 166,730 |
| 按现有代码执行的完整 Mode 编码 | 484,805 |
| 不同完整模板 | 92,893 |
| 带 Flow 快照中，Mode ID 与 Flow Mode ID 相同 | 166,730 / 166,730 |

归档还显示每个前一事务 next Mode 都与后一事务 old Mode 相同，但 Flow
可能被重新建立或清空，因此不能盲目复用整条快照或省略锚点/偏移。
对已有精确 ID 序列进行离线分析，容量为 4 的近期缓存可遇到约 80.69%
的重复 ID；这只说明复用潜力，**不是已实现的编码前缓存或实测提速**。

正确的后续修复是先以可靠的不可变身份或精确内容确认复用，再跳过完整
编码。不能按拓扑、近似浮点数或仅凭 Mode.id 强行合并。

### 4. 完整候选缓存还混合了结构与全部 REG 值

[`candidate_key`](../../src/descriptor.cpp#L21) 包含数值策略、位状态、
本构分段以及全部 REG 的精确值。真实值保持输出变化会改变整个键，
即使某次变化主要体现在观测映射，也可能触发完整模态求解。

全时长原版报告：152,180 次模态编译、225,237 次命中、152,180 次未命中、
152,052 次淘汰。缓存查询未命中率约 **40.32%**；编译数/事务数约 95.69%，
后者不能误称为缓存未命中率。20 ms 诊断中的模态编译路径占普通波形样本
约 14.87%、事件生成样本约 24.37%。

这是次级的结构/动态数据耦合问题，不宜简单删除 REAL 值或扩大缓存来绕过。
REAL 信号也可能进入电气方程和残差检查；依赖分析与所有原状态相关检查
必须保持正确。本调查没有改动这一缓存，也没有改 LU/QR、容差或求根规则。

## 归档缺陷修复目前实际完成到哪里

v2 使用精确共享块，保留 binary64 每一位、原 Flow 锚点和 T128 偏移，
支持有效旧 v1 归档读取。Windows/Linux 正式 Release 均通过 25/25 CTest；
额外历史/PF 回归各为 17 完成、3 项既有 MODEL_SINGULAR，未隐藏这些失败。

Windows v2 已完成 0.5 s 的物理求解和归档：

- 命令发出至 COMPLETED 通知：369.028 s。
- 模板：1,054,309,089 B 的 v1 JSON → 46,426,064 B 的 v2 二进制共享池。
- 全部事件输出：201,313,249 B；原版波形目录为 429,096,088 B。
- 新运行峰值工作集：1,262,268,416 B。
- v1/v2 `segments.bin` 与事件日志的 SHA256 分别相同，关键求解字段未变化。

这些只证明归档生成成功与已检查的状态/记录一致。完整 Windows 回放在
本次根因调查前被暂停，Linux v2 的 0.5 s 事件生成和回放尚未运行，
**不能宣称两平台完整回放或全案例验收通过**。仅 20 ms 诊断波形与事件
回放的所有数组逐字节一致。

## 精度问题单列，不用性能解释掩盖

对未修改且哈希校验的原始 PLECS CSV，两个平台原版的全网格 mean/rms/max
诊断均为 21/21（沿用 channel.atol + 1% 的统计判据）。这不是逐点精度认证。

CH006 在 500,001 个参考点中有 18 个点的绝对差大于 1 V，最大约 528.304 V；
这些点均位于局部电压跳变窗口，且参考时刻与 PULSE 事件的显示时刻重合。
例如 t=0.01 s，参考约 442.139 V，PULSE 当前点约 0.0000776 V，之后 0.1 us
约 221.064 V。不能未经门极时序对照就把它全部解释成单纯左右连续性差异。

精确的 PLECS/PULSE 门极、死区及边界采样差异仍待定位。没有排除这些点来
提高通过率，也未改参考、控制器代码、原子时间或数值规则。

## 证据与复现边界

- 源码：`81dd926bd5c6222c0804db3a0395a2a65404c083`。
- CPU 调查在 WSL2 Ubuntu 原生 ELF 上，GCC 13.3，使用与 Release 相同的 O3/
  严格浮点参数，额外 `-g1 -fno-omit-frame-pointer` 保留诊断栈帧；算法源码不变。
- `perf record -e cpu-clock -F 499 --call-graph fp`；普通输出、事件生成、回放顺序
  采样，窗口明确为 20 ms，而非完整验收；另有 2 ms 初步样本作对照。
- perf 缺少用户态符号解析依赖，新增 `scripts/summarize_perf.py`，用已记录的
  ELF 映射、帧指针栈与 `nm` 符号区间离线解析。未知/不可用调用者保留在分类中。
  采样占比有统计与栈可用性限制，不能把它当作精确计时器。
- [机器可读证据](A010_Root_Cause_Evidence.json) 保留占比、工作量、原版精度、
  短窗口逐字节检查和最小因果实验。原始 perf 数据、完整输出、时间记录和
  对照源码保存在本机 `reports/a010-rootcause-20261102/`、WSL
  `/root/pulse-a010-rootcause-20261102/` 与 `/root/pulse-a010-hoist-diagnostic/`。

应先修输出层重复判断和编码前复用，再验证其无损性；模态求解缓存需要
单独的依赖分析。当前没有改动正式求解器的数值算法，也没有恢复完整长跑。
